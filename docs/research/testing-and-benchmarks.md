# Rendering tests and benchmarks

Research survey for `PLAN.md` (Research survey: "how they test rendering, visual regressions and performance"), milestone M1. Decision: [ADR 0012](../adr/0012-test-tooling.md). Studied on 2026-10-20.

## Scope and requirements served

How VibeGlobeEngine proves its visual and performance targets: render and visual-regression tests, image comparison and tolerances across GPUs and backends, scenario tests with frame capture, frame-time benchmarks, GPU-less CI with software rendering, WebGPU in headless browsers, and the property-based testing and fuzzing libraries.

- `PLAN.md` Testing and verification: visual regression of canonical views on both backends; scenario tests that record frames and detect black pixels, holes and popping; temporal glitch detection (flicker, z-fighting shimmer, seams); benchmarks tracked over time; CI without a GPU runs visual tests on software-rendered WebGL2, WebGPU and performance run on real hardware with a documented procedure; property-based tests with reproducible seeds; fuzzing of every decoder; soak and chaos tests.
- `PLAN.md` Performance and quality targets and the budgets in [quality.md](../plan/quality.md): p95 frame time ≤ 16.7 ms, main-thread CPU ≤ 6 ms p95, GPU ≤ 10 ms p95, zero steady-state allocations, first complete frame ≤ 1 s, zero black pixels, no popping, backend consistency within the visual-test tolerance.
- Features F015 (this survey), F033 (benchmark harness), F043 (property tests), F047, F108, F125 (fuzzing), F061 (zero allocation), F069, F071, F072 (visual regression, software-rendered CI, hardware procedure), F109, F118 (start-up and streaming benchmarks).
- Fixed by [ADR 0002](../adr/0002-monorepo-and-tooling.md): Vitest 5.0.5 and Playwright 1.64.1. Permissive licenses only.

## How each project solves it

### CesiumJS

- **Render tests:** Jasmine specs in Karma. Most rendering specs draw into a 1×1 canvas and check one RGBA value with custom matchers (`toRender`, `notToRender`, `toRenderAndCall`, `toReadPixels` with an optional epsilon). The Testing Guide recommends coarse expectations ("not black") because they hold across WebGL implementations.
- **GPU-less CI:** a WebGL stub turns every GL call into a no-op and the pixel matchers return "pass" without reading anything (`renderEquals` checks `window.webglStub`). CI runs coverage on headless Firefox and release tests on headless Chrome with `--webgl-stub`: code executes, pixels are never verified in CI.
- **Visual regression:** Playwright `toHaveScreenshot` (threshold 0.25, `maxDiffPixelRatio` 0.02) at 960×540, one retry, one worker; the clock is fixed with `page.clock.setFixedTime`/`pauseAt` and advanced with `runFor` because lighting depends on time. Snapshots are gitignored: each developer generates baselines from `main` on their own machine; e2e tests do not run in CI.
- **Benchmarks:** none automated; a manual guide for tileset load time (fixed view, cache disabled, static server).

### MapLibre GL JS

- **Render tests:** 1,734 style-driven tests (`style.json` plus `expected*.png`). The Vitest harness drives Chromium through Puppeteer, creates the map with `fadeDuration: 0`, `preserveDrawingBuffer: true` and no interaction, runs scripted operations (`wait`, `idle`, setters), then reads the framebuffer with `gl.readPixels` at device scale factor 2 instead of taking a page screenshot. pixelmatch compares with threshold 0.1285 and allows 0.025% differing pixels; 92 tests raise the allowance (up to 5%); 141 tests keep several accepted baselines (`expected-ubuntu-22.png`, `expected-win-flaky.png`, `expected-half-float.png` …) and pass if any one matches. One retry, with console logging turned on.
- **GPU-less CI:** `--disable-gpu --enable-features=AllowSwiftShaderFallback,AllowSoftwareGLFallbackDueToCrashes --enable-unsafe-swiftshader`; six shards on Ubuntu and Windows; failures upload an HTML report whose "actual" images become new baselines (`UPDATE=true`).
- **Benchmarks:** micro-benchmarks in `src/**/*.bench.ts` with the Vitest 5 `bench` fixture (`bench.compare`, `writeResult`, `bench.from` for before/after); the README warns that only same-machine, same-session numbers compare. An end-to-end runner times bundle import, style load, first tile, load and idle with performance marks against local fixtures, 8 runs per build, 20% trimmed mean. CI runs the micro-benchmarks but gates nothing on them.

### three.js

- **Visual regression:** every example (615, of which 236 WebGPU) is loaded with an injected deterministic `Math.random`, `performance.now` and `Date.now` frozen at 0, a gated `requestAnimationFrame` that renders exactly one frame on request, and frozen video. After network idle, a page screenshot at 2× is box-downscaled and compared with an RGB-distance metric (0.1 per pixel, at most 0.1% differing pixels) against JPEG (quality 95) baselines. 55 examples sit in an exception list (timeouts, black screens, "rasterizer discrepancies").
- **GPU-less CI:** Ubuntu runners install `mesa-vulkan-drivers` and xvfb and run headful Chrome with `--enable-unsafe-webgpu --enable-features=Vulkan --disable-vulkan-surface --ignore-gpu-blocklist --disable-gpu-watchdog` and `VK_DRIVER_FILES` pointing at Lavapipe, in five shards. A "WebGPU Device Lost" restarts the browser without failing the example.
- **Benchmarks:** no frame-time suite.

### Babylon.js

- **Visualization tests:** 906 scenes in `config.json`, each rendered for `renderCount` frames in per-engine Playwright projects (`webgl2`, `webgpu`), then `gl.getError()` is checked and `toHaveScreenshot` compares with threshold 0.035 and 1.1% allowed pixels (80 scenes raise it, up to 6%); 342 scenes exclude at least one engine; reference images are per engine. CI retries twice and skips scenes whose tags the change does not affect.
- **GPU-less CI:** the WebGL2 and WebGPU visualization suites run on BrowserStack (real macOS GPUs), not on the CI agents. Agent-local conformance tests force `--use-angle=swiftshader --enable-unsafe-swiftshader` "to select a consistent software backend instead of platform-dependent ANGLE defaults".
- **Performance:** the most rigorous method found. A baseline build (CDN) and the candidate run in 10 interleaved rounds with alternating order after 2 warm-up passes; each pass renders 2,500 frames in a tight `scene.render()` loop and records wall time; 2 highest and 2 lowest values are trimmed; a one-tailed paired t-test (p < 0.05) and a ratio above 1.15 must both hold to flag a regression; a coefficient of variation above 10% marks the result inconclusive; suspected regressions get confirmation rounds.

### deck.gl

- **Render tests:** Vitest browser mode with the Playwright provider; 225 golden PNGs; a custom command screenshots the canvas region and runs pixelmatch (color threshold 0.1, anti-aliased pixels ignored) with 99% matching pixels required by default. Specs run `describe.each(['webgl', 'webgpu'])`; the golden is searched in `platform-overrides/{os}/{device}`, `{device}`, `{os}`, then the shared folder, so both backends share one golden unless an override exists. Device loss fails the test.
- **GPU-less CI:** `--use-angle=swiftshader --enable-unsafe-swiftshader`, plus `--enable-unsafe-webgpu --enable-features=Vulkan --use-vulkan=swiftshader` for the separate `test-webgpu` job; failure and diff PNGs are uploaded. Test isolation is off to avoid re-creating contexts per file.
- **Benchmarks:** a `@probe.gl/bench` micro-benchmark suite, not in CI.

### Filament

- **renderdiff:** JSON-declared tests rendered on five renderers: `desktop-opengl`, `desktop-vulkan`, `desktop-webgpu` natively on Mesa's software rasterizers, and `web-webgl`, `web-webgpu` as WebAssembly in headless Chromium on SwiftShader. Goldens are separate per platform and backend, rendered on Linux/aarch64, stored in a separate repository with a branch paired to each pull request, and accepted with a commit-message tag. Tolerance: at most 5/255 per channel, at most 0.1% failing pixels, with per-test presets; dithering is disabled and samples use a fixed timestep.
- **Determinism:** `--force-device-scale-factor=1 --hide-scrollbars --disable-lcd-text --disable-background-timer-throttling --disable-renderer-backgrounding --disable-partial-raster --deterministic-mode`; WebGL adds `--use-angle=swiftshader --enable-unsafe-swiftshader`; WebGPU adds `--enable-unsafe-webgpu --use-webgpu-adapter=swiftshader --enable-features=Vulkan --use-angle=swiftshader --use-vulkan=swiftshader` (the last two give the canvas swap chain a backing on Linux). The harness asserts the pinned browser version and that the rasterizer string contains "swiftshader", and fails otherwise ("fail loudly rather than write junk goldens").
- **On-device validation:** Android goldens compared through tolerance trees with `shiftRadius` and `blurRadius`, so sub-pixel rasterization differences between GPUs pass while color errors do not.
- **Benchmarks:** native Google Benchmark suites with hardware counters; nothing browser-side.

### Measurements in this environment

Throwaway probes on 2026-10-20 in the cloud container (4 vCPUs, no GPU, preinstalled Chromium 141.0.7390.37 driven by Playwright 1.64.1, headless):

- With `--use-angle=swiftshader --enable-unsafe-swiftshader`, WebGL2 reports "ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)), SwiftShader driver)" with `EXT_clip_control`, `EXT_color_buffer_float` and `EXT_disjoint_timer_query_webgl2`.
- Without flags there is no WebGPU adapter. Adding `--enable-unsafe-webgpu --enable-features=Vulkan --use-vulkan=swiftshader --use-webgpu-adapter=swiftshader` gives adapter "google / swiftshader" (`isFallbackAdapter` true; features include `timestamp-query`, `depth-clip-control`, `float32-filterable`); a triangle renders and reads back correctly, and a `webgpu` canvas context works with preferred format `bgra8unorm`. The probe must run on a localhost page: `about:blank` has no `navigator.gpu`.
- Determinism: two browser launches produced bit-identical read-backs and screenshots on both backends (equal SHA-1).
- Backend consistency: the same 640×360 scene with 4× MSAA differs between WebGL2 and WebGPU in 155 pixels (0.067%), all on triangle edges (max channel difference 64). pixelmatch 8.0.0 with anti-aliasing detection reports 0 differing pixels at thresholds 0.05 to 0.2; counting anti-aliased pixels it reports 142 at 0.1.
- Cost: drawing a 1280×720 textured frame, reading it back and scanning it in JavaScript takes 67 ms per frame on SwiftShader.
- `requestAnimationFrame` in headless mode runs at 16.7 ms intervals (p95 16.8 ms), also with `--deterministic-mode`; Playwright's `page.clock` drives `requestAnimationFrame` (62 callbacks per `runFor(1000)`).
- fast-check 4.10.2 prints the seed, the replay path and the shrunk counterexample on failure.

## Literature

The `PLAN.md` references contain no testing papers. The methods here rest on: Kotsarenko and Ramos, YIQ-based perceived color difference (2010), and Vysniauskas, anti-aliased pixel detection (2009), both behind pixelmatch (version 8 switched its color metric to OKLab HyAB distance, so its thresholds are not interchangeable with Playwright's YIQ comparator); Wang et al., SSIM (2004), considered and not chosen; Claessen and Hughes, QuickCheck (ICFP 2000), the model for shrinking property tests; Georges, Buytaert and Eeckhout, statistically rigorous performance evaluation (OOPSLA 2007), Mytkowicz et al., measurement bias (ASPLOS 2009), and Kalibera and Jones, rigorous benchmarking in reasonable time (ISMM 2013), for repeated, interleaved, statistically tested timing.

## Comparison of approaches

- **Rasterizer in CI.** A WebGL stub (CesiumJS) executes code but verifies nothing. SwiftShader (MapLibre, deck.gl, Filament web) ships inside Chromium, covers WebGL2 and WebGPU, and is bit-deterministic (measured), but its transcendental functions are inaccurate (deck.gl#10804), it is slow, and its timings say nothing about real GPUs. Mesa Lavapipe (three.js, Filament desktop) needs system packages and fragile driver paths that Chromium may silently ignore (three.js#33559). Cloud GPUs (Babylon.js) are realistic but per-device and external. Only local hardware measures performance.
- **Capture.** Engine read-back (MapLibre, Filament) ties an image to one engine frame and excludes the compositor and DOM; page screenshots (the others) also cover presentation and overlays but are asynchronous to frames. WebGPU read-back needs `COPY_SRC` on the canvas texture and 256-byte row alignment, and the Linux SwiftShader format is BGRA; WebGL2 reads after the draw or with `preserveDrawingBuffer`.
- **Comparator.** pixelmatch with anti-aliasing detection absorbs edge-coverage differences between backends (measured: 155 → 0 pixels). Absolute per-channel limits (Filament, three.js) are simple but count every edge pixel. Shift tolerance (Filament devices) absorbs sub-pixel rasterization differences between GPUs without loosening colors. SSIM is structure-based and can hide small local defects such as a one-tile hole.
- **Baselines.** Several accepted baselines per test (MapLibre) decay into "expected-win-flaky"; local-only baselines (CesiumJS) give no CI signal; per-backend baselines from one pinned environment (Filament, Babylon.js) are reproducible; shared cross-backend goldens (deck.gl) enforce consistency but break when backends legitimately differ in filtering.
- **Determinism controls.** Fixed engine clock (CesiumJS, MapLibre `setNow`, three.js, Filament), seeded randomness (three.js), disabled fades (MapLibre), capture after engine idle rather than network idle (cesium#12281, three.js#33559), pinned browser plus rasterizer assertion (Filament).
- **Performance.** Micro-benchmarks (MapLibre, deck.gl) catch hot-path regressions but not frame pacing; load-time milestones (MapLibre) cover start-up only; interleaved A/B with statistics (Babylon.js) is the only method robust to machine drift; frame intervals on a vsync-locked display quantize to 16.7 ms and hide regressions until a budget breaks, so regression detection must compare CPU and GPU work time per frame, not intervals.
- **WebGPU versus WebGL2.** WebGPU timestamps are quantized to 100 µs unless Chrome's WebGPU developer features are enabled; WebGL2 timer queries are not universally exposed; device loss on WebGPU is an event to assert, never a reason to skip (three.js#33559).

## Chosen approach for VibeGlobeEngine

Recorded in [ADR 0012](../adr/0012-test-tooling.md):

1. **Tools.** Vitest 5 for unit, property, fuzz and micro-benchmark tests (built-in `bench` fixture, tinybench 6.2.2, no new benchmark dependency); Playwright 1.64 Test for visual, scenario, chaos and performance tests driving the playground; `@vitest/browser-playwright` 5.0.5 (MIT) for renderer tests that need a real GPU device (M2). New development dependencies: `pixelmatch` 8.0.0 (ISC), `pngjs` 7.0.0 (MIT) with `@types/pngjs` 6.0.5 (MIT), `fast-check` 4.10.2 (MIT), `@fast-check/vitest` 0.5.0 (MIT), `@fast-check/worker` 0.6.0 (MIT).
2. **CI without GPU.** Both backends run in CI on SwiftShader in Chromium's new headless mode: WebGL2 with `--use-angle=swiftshader --enable-unsafe-swiftshader`, WebGPU additionally with `--enable-unsafe-webgpu --enable-features=Vulkan --use-vulkan=swiftshader --use-webgpu-adapter=swiftshader`. Every test asserts the pinned browser version, the SwiftShader renderer or adapter and the engine's active backend, and fails otherwise. This changes `quality.md`, which skipped WebGPU in CI; WebGPU performance stays on hardware.
3. **Capture and comparison.** Engine read-back (not page screenshots) at 960×540, device pixel ratio 1, plus a 2× subset; PNG baselines per backend generated only in the pinned CI environment; one comparator (pixelmatch 8 with anti-aliasing detection) behind a small helper that honors `--update-snapshots` and attaches expected, actual and diff images.
4. **Tolerances.** Same rasterizer and backend: threshold 0.05, at most 0.01% differing pixels. WebGPU against WebGL2 in the same run: threshold 0.1, at most 0.1%. Real GPUs against the CI baselines: threshold 0.1 with a 1-pixel shift allowance, at most 0.2% (calibrated in M2). Defect detectors (sentinel pixels, popping, flicker, seams) are invariant checks with zero tolerance, independent of baselines.
5. **Benchmarks.** Scripted scenarios on real hardware (headed, 1 warm-up and 5 measured runs, median of per-run p95 against `quality/budgets.json`), interleaved A/B on CPU and GPU work time for regressions, deterministic counters gated in CI, micro-benchmarks next to hot paths.
6. **Flakiness.** `retries: 1` with `failOnFlakyTests: true` in CI: the retry collects a trace, but a pass on retry still fails the run.

### What must still be measured

- **M1:** repeat the determinism, backend-consistency and cost probes on Playwright 1.64.1's own Chromium 156.0.8078.4 on the CI runner (the container has 141); confirm that `--deterministic-mode` changes no frame pacing; time one canonical view per backend in CI.
- **M2:** calibrate the hardware tolerance on the reference desktop devices (all canonical views, record the benign distribution, set the limit at twice the worst benign value and never above 0.5%); prove the CI tolerance fails on a changed shader color and on a 1-pixel geometry shift (F069).
- **M3:** validate every scenario detector against injected defects (missing tile, fade bypass, one-pixel seam, z-fighting pair): each must fail its defect and pass the clean run; measure capture overhead and the run-to-run coefficient of variation of p95 frame time on the reference desktop (target below 5%).
- **M3–M4:** fuzz throughput per decoder, to size the CI and nightly input budgets.

## Open questions

- Baseline storage: plain PNG in git until about 50 MB in total, then Git LFS or a separate assets repository (Filament's model); decision in M2.
- Cloud sessions use Chromium 141 while baselines come from Chromium 156: can sessions install the pinned browser (`npx playwright install chromium`), or must baseline updates always run in CI? Comparisons on other browsers are advisory, as in Filament.
- Whether coverage-guided fuzzing (Jazzer.js, Apache-2.0, built on libFuzzer and oriented to Jest) adds value over fast-check for the terrain and vector decoders (revisit in M4).
- Firefox and Safari WebGPU cannot run in Linux CI; they rely on the hardware procedure and the owner's devices (open questions 2 and 6).
