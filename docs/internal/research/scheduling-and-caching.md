# Tile scheduling and caching

Survey written in M1; the scheduler, the RAM and GPU caches and the upload budget are built in M3 (flight preloading and bandwidth adaptation plug into them in M8). Decision: [ADR 0007](../adr/0007-scheduling-and-caching.md).

## Scope and the requirements it serves

How tile requests are ordered, throttled, cancelled, retried and timed out, how duplicate work is avoided, and how decoded tiles are kept within memory and upload budgets. Requirements served:

- `PLAN.md`, Tiles, level of detail and streaming: priorities (screen center first, coarse before fine, visible before prefetch), concurrency limits per host, cancellation "essential during flights", retries with backoff, timeouts, 404 and out-of-coverage as no data, frame budget for uploads, memory budgets with LRU eviction, pinned base never evicted, flight preloading, motion-aware detail.
- `PLAN.md`, Engineering standards: request coalescing, never the same tile downloaded twice, render on demand, no garbage in hot paths.
- `docs/internal/plan/architecture.md` §2 (steps 7–8), §6 (tile states), §7 (loading pipeline), §8 (memory reuse switch), §14 (a failing tile never blanks the view).
- `docs/internal/plan/quality.md`: uploads ≤ 2 ms and ≤ 8 MB per frame; GPU 512/256 MB and RAM 256/128 MB (desktop/tablet); 0 duplicate tile downloads per session; first complete frame ≤ 1 s from a LAN base.
- Feature list: F084, F088–F093, F095–F096, F098, F101, F113, F115, F121 (M3); F222, F265 (M7); F281–F285, F300–F303 (M8); F462 (M13).

Out of scope, covered by their own surveys: tile selection and screen-space error (`level-of-detail.md`), the worker pool (`workers.md`), GPU resource internals (`gpu-and-renderer.md`), persistent storage, packages and bandwidth estimation (`offline-and-network.md`, M8).

## How each project solves it

### CesiumJS

- **Request layer.** A module-level `RequestScheduler` (shared by every viewer on the page) caps active requests at 50 overall and 18 per server key (authority plus port; `requestsByServer` overrides it, documented for HTTP/2 hosts). Throttled requests enter a binary heap bounded at 20 entries: inserting into a full heap evicts and cancels the worst request, and `request()` returns `undefined` when the server or the heap is saturated, so the caller simply asks again next frame. `update()` runs once per frame: it drops settled requests, re-evaluates each queued request's `priorityFunction`, re-sorts the heap and fills free slots; a request whose server is full at that moment is cancelled. Cancelling rejects the request's promise and calls its `cancelFunction` (`xhr.abort()`); images loaded through an `<img>` element cannot be aborted, only those fetched as blobs for `createImageBitmap`. Results of cancelled requests are ignored.
- **Globe priorities.** Terrain and imagery requests bypass the heap (`throttle: false`) and are limited only per server. Order comes from `QuadtreePrimitive`'s three load queues: high (tiles preventing refinement), medium (rendered tiles), low (preloaded ancestors and siblings), each sorted by `computeTileLoadPriority` = (1 − cosine of the angle off the view direction) × distance, and processed within a 5 ms time slice per frame (at least one tile always). `loadingDescendantLimit` (20) caps how many not-yet-renderable descendants are queued before the intermediate tile is loaded instead.
- **3D Tiles priorities.** `Cesium3DTile.updatePriority` packs criteria into decimal digits: flight-destination flag, foveated deferral, foveated factor, progressive-resolution flag, distance or reverse screen-space error, then depth. Requested tiles are sorted before issuing ("less likely to be cancelled after being issued"); `cancelOutOfViewRequests` cancels in-flight requests for tiles not touched this frame; `cullRequestsWhileMoving` skips requests predicted to be off screen on arrival; `preloadFlightDestinations` runs a traversal from the flight's destination camera.
- **Retries and timeouts.** `Resource.retryCallback`/`retryAttempts` (default 0) are application hooks, applied only to real failures, not cancellations; imagery failures raise a `TileProviderError` whose listener may request a retry. No backoff, no timeout.
- **Caches.** Globe tiles live in `TileReplacementQueue`, an intrusive doubly linked LRU counted in tiles (`tileCacheSize` 100). At the start of each frame it remembers the current head; `trimTiles` walks from the tail and stops at that marker, so nothing used this frame is evicted (the count is a soft limit) and tiles mid-load are skipped. 3D Tiles use `Cesium3DTilesetCache`, a linked list split by a sentinel into "not selected this frame" and "selected this frame", trimmed to `cacheBytes` (512 MiB). `maximumCacheOverflowBytes` lets the working set exceed the budget; above it, `memoryAdjustedScreenSpaceError` grows 2% per frame until the selection fits, and shrinks again below budget.

### MapLibre GL JS

- **Order.** `coveringTiles` returns ideal tiles sorted by squared distance to the center; `TileManager` creates and loads them in that order, retaining loaded parents and children as fallbacks.
- **Throttle.** Raster images go through a global FIFO (`ImageRequest`): 16 parallel requests, or 8 while any registered throttle control (an application callback such as "map is moving") returns true. There is no per-host limit and no reprioritization; vector tiles are fetched in workers and throttled only by the browser.
- **Cancellation.** Each tile owns an `AbortController`; removing an unfinished tile aborts it, aborted queue items are skipped, and the `<img>` path cancels by clearing `src`. Worker tasks are cancelled by a `<cancel>` message; the worker processes one task per message-channel tick so cancels can overtake queued work. `cancelPendingTileRequestsWhileZooming` (default on) stops retaining parents that have no data yet, so their requests are aborted during zoom (introduced after [#2577](https://github.com/maplibre/maplibre-gl-js/issues/2577)).
- **Errors.** A 404 marks the tile errored without an event and re-runs fallback selection; other errors fire an event. No retry or timeout; errored tiles reload only when the source changes. An empty 204 response is a transparent tile, distinct from a 404.
- **Cache.** An out-of-view `TileCache` keyed by tile id, counted in tiles: about tiles-per-viewport × 5 zoom levels, optionally capped by `maxTileCacheSize`, with per-tile expiry timers from `Cache-Control`/`Expires`. Its order array uses `indexOf`/`splice` (linear time). Tile textures are recycled by size.

### OpenLayers

- **Queue.** One `TileQueue` per map, a keyed binary heap. Priority = 65536·ln(resolution) + distance to the view center ÷ resolution: the finest wanted level first, then center distance. Tiles no longer in the frame's `wantedTiles` get `DROP` and leave the heap when it is re-heapified after each render.
- **Throttle.** `loadMoreTiles` allows `maxTilesLoading` (16) in flight at rest; while animating or interacting, 8 in flight and 2 new per frame, and none at all when the frame already took more than 8 ms. Dequeue skips tiles that are not idle (fix for [#3889](https://github.com/openlayers/openlayers/issues/3889)).
- **Preload.** The `preload` option enqueues coarser levels after a `setTimeout`; during an animation, tiles of the final view (`frameState.nextExtent`) are enqueued too, a simple destination preload.
- **Cancellation and errors.** Image tiles load through `<img>` and are never aborted; `DROP` only affects queued tiles. Errors leave the tile in `ERROR`; retries need a custom `tileLoadFunction` (the docs suggest retrying 408, 429, 500, 502, 503, 504). No timeout.
- **Cache.** Each tile-layer renderer keeps an `LRUCache` (512 entries), whose high-water mark grows to twice the wanted tile count; it expires entries after a complete render.

### Leaflet

- No scheduler: `GridLayer._update` computes the visible tile range, sorts missing tiles by distance to its center and inserts all their `<img>` elements at once. The browser's per-host connection limit is the only throttle (hence `{s}` subdomains). Updates are throttled to one per 200 ms while panning, or deferred to the end of the move on mobile.
- Cancellation happens only when the zoom level changes: `_abortLoading` points incomplete tiles of other levels at an empty data URL and removes them. Tiles panned out of view keep downloading.
- Fallback: `keepBuffer` (2 tile rows) around the view; a missing tile keeps a loaded ancestor up to 5 levels up or descendants 2 levels down. No cache beyond the DOM: removed tiles come back from the browser's HTTP cache. `errorTileUrl`, no retry, no timeout.

### loaders.gl

- `RequestScheduler` hands out slots instead of performing requests: `scheduleRequest(handle, getPriority)` resolves to a `done()` token once a slot frees (6 by default, 64 in `Tileset3D`), or to `null` if cancelled. A repeated handle gets the same promise (coalescing). Whenever a slot frees, every queued priority is re-evaluated and the queue re-sorted; a negative priority cancels. In-flight requests are never aborted; `debounceTime` lets a moving camera settle.
- `Tile3D._getPriority` cancels tiles not touched this frame and otherwise uses root error minus parent error (coarse first). The tile cache is the Cesium sentinel list trimmed to `maximumMemoryUsage` (32 MB), with an opt-in memory-adjusted screen-space error (×1.02 per update over budget plus overflow).

### 3DTilesRendererJS

- **Queues.** Three priority queues shared by all renderers: downloads (one queue per URL origin, 25 jobs each), parsing (5), node preprocessing (25). Each run, scheduled on `requestAnimationFrame`, sorts with a comparator: used tiles, then higher error, then distance, then shallower depth; or, in the optimized traversal, used, in frustum, external tileset, distance.
- **Cancellation.** A tile load carries an `AbortController` fired when the LRU removes the tile, checked between download, parse and processing. `removeUnusedPendingTiles` drops only queued tiles, deliberately leaving in-flight ones that "may already be nearly downloaded".
- **Cache.** `LRUCache` with hysteresis on both counts (6000/8000 tiles) and bytes (0.3/0.4 GiB). `unloadUnusedContent` sorts the whole list (unused first; least recently visited, deeper, less loaded first) and evicts at most 5% of the excess per run, rescheduling itself to spread the cost. `add()` refuses tiles when the cache is full, which blocks downloads; refusals have been counted in `stats.refused` since [#1722](https://github.com/NASA-AMMOS/3DTilesRendererJS/issues/1722). Failures are terminal (`FAILED`, `load-error` event).

### iTowns

- `Scheduler` keeps one queue per host (6 commands in flight), each holding a priority queue per layer; the next layer is picked by smooth weighted round-robin on `layer.priority`, so layers sharing a host stay fair. Command priority is 100 for visible materials and 10 otherwise; an `earlyDropFunction` checked at dequeue discards commands for tiles no longer visible, removed layers or elevation already finer. In-flight work is never aborted.
- `LayerUpdateState` gates retries: waits of 1, 3, 7 and 60 s after successive errors; after 4 retries the error is definitive; a parse error is definitive at once. No-data answers record the lowest failing level, and later requests bisect toward the finest available level.
- `Layer.cache` is an LRU of 500 entries holding promises, so concurrent and repeated requests for one key share a single fetch; an optional TTL expires entries.

### Potree

- Visibility traversal uses a binary heap keyed by projected node size, under a visible point budget (1 M points). Up to `maxNodesLoading` (4) unloaded nodes start per update in priority order, guarded by a global in-flight counter. No cancellation; a failed load resets the node to unloaded and is retried on the next traversal, with no backoff.
- An intrusive LRU counts loaded points; while above `pointLoadLimit`, `freeMemory` disposes the least recently used node together with all its descendants.

Two patterns dominate. Stalls come from in-flight counters that leak on an unusual exit path (error, disposal, sharing, abort) or from silent admission refusals; and wasted downloads come from requests that cannot be aborted or are aborted too late. None of the studied projects has request timeouts, and only iTowns has backoff (a fixed schedule; loaders.gl planned retries with backoff in [#754](https://github.com/visgl/loaders.gl/issues/754) but closed it undone).

## How they test and benchmark loading

- **CesiumJS:** Jasmine specs in real browsers. RequestSchedulerSpec (31 cases) covers global and per-server caps, heap length, priority updates, cancelling issued and active requests, no unhandled rejection, statistics; QuadtreePrimitiveSpec drives selection with mock providers (load priority, `loadingDescendantLimit`); Cesium3DTilesetSpec covers `cacheBytes` unloading, overflow bytes, "cancels out-of-view tiles", "sorts requests by priority", foveated deferral. Benchmarks are manual: the Performance Testing Guide (fixed camera, browser cache disabled, time until tiles are loaded) and development Sandcastles for 3D Tiles and terrain. No automated load-time tracking.
- **MapLibre GL JS:** Vitest with fake servers and timers: image_request.test (parallel cap, a cancel frees a slot, a 404 keeps the queue moving, throttling), tile_manager.test (aborts unfinished tiles, caches loaded ones, suppresses 404 errors, retains parents for pending children, expiry timers), tile_cache.test. Benchmarks: Vitest micro-benchmarks with recorded baselines, and an end-to-end benchmark that loads built artifacts in headless Chrome against local fixtures with zero network and times bundle import, style load, first tile, load and first idle across versions.
- **OpenLayers:** TileQueue tests (error tiles with and without retry, shared queues), node tests for PriorityQueue and LRUCache, and rendering tests that compare screenshots after `rendercomplete`. No loading benchmark.
- **Leaflet:** GridLayerSpec counts tiles loaded and unloaded for scripted zoom and pan sequences ("Loads 32, unloads 16 tiles zooming in 10-11", keepBuffer variants).
- **loaders.gl:** request-scheduler.spec (scheduling, debounce, changing limits with active requests); module benchmarks measure parsing only.
- **3DTilesRendererJS:** Vitest units for LRUCache (byte limits, used items, size rounding), PriorityQueue, DownloadPriorityQueue (per-origin independence, removal on abort), TilesRendererBase (`stats.refused`). No loading benchmark.
- **iTowns:** a unit test that the scheduler runs 100 commands and balances layers; Puppeteer functional tests on examples, flaky for lack of a stable signal (#2530).
- **Potree:** no automated tests.

Everyone unit-tests the scheduler with fake transports; nobody runs automated scenario tests that assert zero duplicates, bounded wasted bytes or freedom from stalls. MapLibre's local-fixture end-to-end benchmark is the best model for load timing.

## Literature

- **Cozzi and Ring (2011)** prepare resources on worker threads behind message queues so the render thread never blocks, and treat out-of-core terrain as prioritized requests plus a bounded cache with a replacement policy and prefetching. That is the shape adopted here.
- **Ulrich (2002), chunked LOD:** chunks are paged asynchronously as the LOD metric approaches needing them; a parent stays drawn until all its children are resident, and chunks whose LOD makes them unnecessary are unloaded. This is the contract behind parent fallback plus eviction.
- **Losasso and Hoppe (2004), geometry clipmaps:** levels update coarse to fine under a per-frame budget; when the viewer moves faster than updates complete, finer levels are left out and coarser ones render. This is the model for coarse-before-fine ordering, the upload budget and motion-aware detail.
- **van Wijk and Nuij (2003):** the flight path is analytic, so the views a `flyTo` will pass through, and when, are known when it starts. That makes destination preloading and deadline-aware path requests possible (M8).

## Comparison of approaches

| Aspect         | Approaches seen                                                                                                                                                                                                 | Trade-offs and failure modes                                                                                                                                                                                               |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Queue          | Bounded heap, re-requested every frame (Cesium); persistent queue re-prioritized with drops (OpenLayers, loaders.gl, 3DTilesRendererJS, iTowns); FIFO sorted once (MapLibre); the browser's own queue (Leaflet) | A FIFO goes stale during motion. **WebGPU and WebGL2.** Upload cost differs by backend and must be budgeted per backend: on WebGL2, `texImage2D` from an `ImageBitmap` runs synchronously on the calling thread and may convert or flip pixels; on WebGPU, `copyExternalImageToTexture` is queued to the GPU process and returns sooner. Mipmap generation is a driver call on WebGL2 but needs render or compute passes on WebGPU (three.js provides them). Releasing memory is deterministic on WebGPU (`texture.destroy()`) and deferred by the driver on WebGL2, so the engine keeps its own byte accounting on both. Only WebGPU reports allocation failure (`out-of-memory` error scopes); on WebGL2 the only signal is context loss, so budgets must be conservative there.

## Chosen approach for VibeGlobe

Full specification and defaults in [ADR 0007](../adr/0007-scheduling-and-caching.md). In short:

1. **One scheduler per engine instance over a page-wide network pool.** The pool (reference-counted like the worker pool, created lazily) owns host slots, per-source rate limits and in-flight coalescing by request key, so per-host and provider-profile limits hold across instances, as in Cesium and 3DTilesRendererJS. Each instance owns its priorities, queue and caches.
2. **Persistent pooled request records in a binary heap rebuilt every frame** from the wanted list (linear heapify, no allocation). The priority key is class first: base, visible, flight destination, flight path, prefetch. Within a class the key is the tile level plus a screen-distance term from the focus point (the screen center, or the cursor during anchored zoom). Unwanted queued records are dropped at the end of the frame for free. Free slots are refilled immediately when a request settles, not only once per frame.
3. **Concurrency:** 6 per host by default (16 for hosts declared or detected as HTTP/2 or HTTP/3), 32 overall, lower caps from provider profiles, token-bucket rate limits from source metadata. The scheduler never hands the browser more than these caps, so everything waiting stays reprioritizable. No frame-time gating of the network.
4. **Cancellation:** all requests use `fetch` with an abort signal. In-flight requests unwanted for 2 frames and at least 100 ms are aborted; a coalesced request only when no consumer wants it any more. Unstarted decode tasks and pending uploads of unwanted tiles are dropped, and their downloaded bytes are kept.
5. **Failures:** 404, 410, 204 and out-of-coverage mean no data (terminal, remembered in a per-source negative set); 408, 429, 5xx, network errors and timeouts retry with full-jitter exponential backoff (0.5 s base, 30 s cap, 4 retries, `Retry-After` honored) as an eligibility gate that only applies while the tile is wanted; a host circuit breaker drops to 1 probe after repeated failures. Timeouts are 10 s to headers and 30 s total. Slot release is structural (one `finally` path), with a stall watchdog in tests.
6. **Memory:** byte-accounted GPU and RAM tiers with hard budgets. The RAM tier keeps encoded bytes for every GPU-resident tile (so context loss can be recovered and nothing is downloaded twice); decoded copies are transient. Eviction uses an intrusive LRU with a frame marker, touched in post-order so children are evicted before parents; pinned base, render set, fallbacks and fading tiles are protected. Eviction runs with hysteresis (down to 90%) and is spread across frames. Predicted bytes are reserved at dispatch; when the protected set cannot fit, the tile is refused, counted and reported, and the selection's error threshold rises until it fits (Cesium's memory-adjusted error, but without overflow).
7. **Pinned base** levels 0..N per base source, N automatic within 1/8 of the GPU budget, loaded first and never evicted.
8. **Uploads** drain in priority order within 2 ms and 8 MB per frame, with a per-backend cost model; items larger than the budget are sliced across frames.

**To measure in M3** (fixture tile server with controllable latency, bandwidth and failures, over HTTP/1.1 and HTTP/2; Playwright scenarios with request logs; results in `benchmarks/results/`):

- Per-host concurrency of 4, 6, 8 and 16 on HTTP/1.1 and HTTP/2: time to a sharp center, time to a complete view, and p95 frame time.
- In-flight abort policy (immediate, 2 frames plus 100 ms, never after headers) on the Milan to Tokyo path: wasted bytes, connections opened, and time to a complete destination.
- Weight of the center-distance term (0, 1, 2 and 4 levels): order of completion after a jump (F088).
- Upload budget adherence on WebGPU and WebGL2 during a burst of 200 arrivals (F101): every frame within 2 ms and 8 MB, and the number of frames to drain.
- Scheduler update cost with 5,000 wanted tiles: at most 0.3 ms p95, with zero allocations in steady state.
- Eviction cost per frame and the hysteresis band under a small budget (F098); memory never above budget.
- Pinned-base size against time to first complete frame from a LAN server (F115, at most 1 s).
- Duplicate downloads per session in all scenarios: must be 0 when the budget holds the session's working set; re-downloads after eviction are reported separately.

## Open questions

- Can the HTTP version of a cross-origin host be detected reliably (Resource Timing's `nextHopProtocol` without `Timing-Allow-Origin`), or must sources declare it?
- Does aborting on HTTP/1.1 cost a new TLS connection in every target browser, and should the abort grace then depend on the protocol? Answered by the M3 abort measurement.
- Fairness between engine instances sharing the pool (for example a main view and a minimap): is class-then-key priority enough, or is weighted round-robin needed as in iTowns?
- How 3D Tiles (M13) share slots with terrain and imagery without starvation (cesium#5509): one key space may suffice, or category rotation may be needed.
- Merging byte ranges for PMTiles and Cloud Optimized GeoTIFF sources (openlayers#16961) belongs in the source adapters (M7); the scheduler may need a batching hook.
- Whether the fetch `priority` hint (high for base and visible, low for prefetch) measurably helps on HTTP/2 in each browser.
