# Depth precision

Survey for milestone M2 (written during M1). Decision: [ADR 0005](../adr/0005-depth-strategy.md).

## 1. Scope and requirements

A globe view can show geometry at 0.5 m and at more than 10,000 km in the same frame. The depth buffer has to order surfaces only a few centimeters apart at every distance, on WebGPU and on WebGL2, without costing frame time. This survey covers depth encodings (standard, reversed-Z, logarithmic), depth formats, near and far planes, and multi-frustum rendering. Vertex position precision (relative-to-center and relative-to-eye) belongs to the precision survey. Depth is only as good as the float32 view-space distance that feeds it, so the two decisions depend on each other.

Requirements served:

- `PLAN.md`, Rendering and visual quality: "no z-fighting between near and far geometry in the same view".
- `PLAN.md`, M2 done-when: "zooming from orbit to about 1 m above the ground shows no jitter and no z-fighting on both backends".
- `feature_list.json` F055: camera 1 m above ground, test geometry from 0.5 m to the horizon, surfaces a few centimeters apart resolve in the correct order, with no pixel alternating between frames, on WebGPU and forced WebGL2.
- Draping and data layers (`PLAN.md`; [architecture](../plan/architecture.md) §10): no shapes floating above or cutting into terrain.
- Engineering standards: performance budgets (`docs/plan/quality.md`, GPU ≤ 10 ms p95), and the same result on both backends in every supported browser (Chrome, Edge, Firefox, Safari).

## 3. How each project handles near and far geometry

**CesiumJS: logarithmic depth by default, multi-frustum underneath.** `Scene.defaultLogDepthBuffer = true` ([Scene.js L800](https://github.com/CesiumGS/cesium/blob/1.146/packages/engine/Source/Scene/Scene.js#L800)); with log depth the camera defaults to near 0.1 m and far 1e10 m ([L726](https://github.com/CesiumGS/cesium/blob/1.146/packages/engine/Source/Scene/Scene.js#L726)). Each frame `createPotentiallyVisibleSet` culls every command and measures its bounding-volume distance along the view direction. This gives a fitted near and far, clamped to the camera's. `updateFrustums` then splits [near, far] geometrically into `ceil(log(far/near)/log(ratio))` frustums ([View.js L170](https://github.com/CesiumGS/cesium/blob/1.146/packages/engine/Source/Scene/View.js#L170)). The ratio is `farToNearRatio = 1000` with a normal depth buffer and `logarithmicDepthFarToNearRatio = 1e9` with log depth ([Scene.js L383](https://github.com/CesiumGS/cesium/blob/1.146/packages/engine/Source/Scene/Scene.js#L383)). Commands are binned into every frustum they overlap. The frustums draw back to front with a depth clear between them, and the near plane of all but the closest is pulled in by `opaqueFrustumNearOffset = 0.9999` to hide tearing at the seams ([L2847](https://github.com/CesiumGS/cesium/blob/1.146/packages/engine/Source/Scene/Scene.js#L2847), [L1748](https://github.com/CesiumGS/cesium/blob/1.146/packages/engine/Source/Scene/Scene.js#L1748)). A depth-only ellipsoid (`DepthPlane`) stops geometry behind the globe from showing through in farther frustums, and globe depth is copied per frustum for picking.

The log depth itself is a per-fragment write: the vertex stage passes `w − near + 1` and clamps clip z so nothing is clipped early. The fragment stage writes `gl_FragDepth = log2(d)/log2(far − near + 1)`, discards fragments outside the frustum's range, and emulates polygon offset by hand ([writeLogDepth.glsl](https://github.com/CesiumGS/cesium/blob/1.146/packages/engine/Source/Shaders/Builtin/Functions/writeLogDepth.glsl#L25), [vertexLogDepth.glsl](https://github.com/CesiumGS/cesium/blob/1.146/packages/engine/Source/Shaders/Builtin/Functions/vertexLogDepth.glsl)). Every shader in the engine has to call these functions.

**three.js r186: both options exist, but neither is complete on its own.**

- `WebGLRenderer({ reversedDepthBuffer })` requires `EXT_clip_control`; without it, it warns and falls back to standard depth ([WebGLCapabilities.js L96](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLCapabilities.js#L96)). With it, it calls `clipControlEXT(LOWER_LEFT, ZERO_TO_ONE)`, inverts compare functions through `ReversedDepthFuncs`, and clears depth to 0 ([WebGLState.js L78](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLState.js#L78)). The projection is a finite-far reversed [0,1] matrix ([Matrix4.js L1140](https://github.com/mrdoob/three.js/blob/r186/src/math/Matrix4.js#L1140)).
- `WebGPURenderer({ reversedDepthBuffer })` needs nothing more on WebGPU. Its WebGL2 backend applies the same `EXT_clip_control` test and falls back by resetting `renderer.reversedDepthBuffer` to false ([WebGLBackend.js L276](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl-fallback/WebGLBackend.js#L276)).
- Reversed-Z only pays off with a float depth buffer, and r186 gets one only in some places:
  - The canvas depth on the WebGPU backend becomes `depth32float` ([WebGPUUtils.js L70](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgpu/utils/WebGPUUtils.js#L70)), and so does `PassNode` depth ([PassNode.js L806](https://github.com/mrdoob/three.js/blob/r186/src/nodes/display/PassNode.js#L806)).
  - Any other render target without an explicit depth texture gets `UnsignedIntType`, which maps to `depth24plus` or `DEPTH_COMPONENT24` ([Textures.js L94](https://github.com/mrdoob/three.js/blob/r186/src/renderers/common/Textures.js#L94)). That includes the internal output target used whenever tone mapping or sRGB conversion is on, which is the default.
  - Only an explicit `DepthTexture` of `FloatType` gives `DEPTH_COMPONENT32F` on WebGL2 ([WebGLTextureUtils.js L296](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl-fallback/utils/WebGLTextureUtils.js#L296)), which the WebGL example does explicitly ([webgl_reversed_depth_buffer.html L120](https://github.com/mrdoob/three.js/blob/r186/examples/webgl_reversed_depth_buffer.html#L120)).
  - PR [#34803](https://github.com/mrdoob/three.js/pull/34803) makes the default float for r187, after r186.
- Logarithmic depth:
  - On `WebGLRenderer` it is `gl_FragDepth = log2(1 + w) · logDepthBufFC/2` with `logDepthBufFC = 2/log2(far + 1)`, the Outerra formula with near ignored ([logdepthbuf_fragment.glsl.js](https://github.com/mrdoob/three.js/blob/r186/src/renderers/shaders/ShaderChunk/logdepthbuf_fragment.glsl.js)).
  - On `WebGPURenderer` it is a TSL depth node `log2(−z/near)/log2(far/near)` (Ulrich's formula). It is written as `frag_depth` in WGSL and `gl_FragDepth` in GLSL ([NodeMaterial.js L677](https://github.com/mrdoob/three.js/blob/r186/src/materials/nodes/NodeMaterial.js#L677), [ViewportDepthNode.js L251](https://github.com/mrdoob/three.js/blob/r186/src/nodes/display/ViewportDepthNode.js#L251)).
  - `setupDepth` takes a material's own `depthNode` first. That gives an engine a supported hook for custom depth output.
  - Log depth and reversed depth are not combined: the log node ignores `reversedDepthBuffer`. Maintainers now recommend reversed depth and plan to deprecate log depth ([#29841](https://github.com/mrdoob/three.js/issues/29841)).

**Babylon.js: reversed depth that works on WebGPU but not on WebGL, plus log depth per material.**

- `engine.useReverseDepthBuffer` switches the depth function to `GEQUAL` and the clear value to 0 ([abstractEngine.pure.ts L530](https://github.com/BabylonJS/Babylon.js/blob/52ffb86179eaa2996e2babc77ef33a374b708b76/packages/dev/core/src/Engines/abstractEngine.pure.ts#L530)), and the camera swaps `minZ` and `maxZ` in the projection ([camera.pure.ts L969](https://github.com/BabylonJS/Babylon.js/blob/52ffb86179eaa2996e2babc77ef33a374b708b76/packages/dev/core/src/Cameras/camera.pure.ts#L969)); `ignoreCameraMaxZ` gives a reversed infinite-far matrix ([math.vector.pure.ts L8496](https://github.com/BabylonJS/Babylon.js/blob/52ffb86179eaa2996e2babc77ef33a374b708b76/packages/dev/core/src/Maths/math.vector.pure.ts#L8496)).
- The WebGL engine never calls `EXT_clip_control`, so its reversed depth still lands in [−1,1] clip space. Babylon's own visual test "Reverse depth buffer fix flicker" is excluded on WebGL1 and WebGL2 ([config.json L2798](https://github.com/BabylonJS/Babylon.js/blob/52ffb86179eaa2996e2babc77ef33a374b708b76/packages/tools/tests/test/visualization/config.json#L2798)).
- On WebGPU the main pass uses `depth32float` only when stencil is off. The `stencil` option defaults to true, which gives `depth24plus-stencil8` ([webgpuEngine.pure.ts L1132](https://github.com/BabylonJS/Babylon.js/blob/52ffb86179eaa2996e2babc77ef33a374b708b76/packages/dev/core/src/Engines/webgpuEngine.pure.ts#L1132)).
- `material.useLogarithmicDepth` writes the log value both to `gl_Position.z` and to the fragment depth, with constant `2/log2(maxZ + 1)` ([logDepthVertex.fx](https://github.com/BabylonJS/Babylon.js/blob/52ffb86179eaa2996e2babc77ef33a374b708b76/packages/dev/core/src/Shaders/ShadersInclude/logDepthVertex.fx), [materialHelper.functions.ts L39](https://github.com/BabylonJS/Babylon.js/blob/52ffb86179eaa2996e2babc77ef33a374b708b76/packages/dev/core/src/Materials/materialHelper.functions.ts#L39)).

**Filament: reversed-Z, infinite far and float depth, always on.**

- The user projection follows GL conventions. For rendering, the far plane is always moved to infinity, and the matrix is converted to an "inverted DX" clip space with near = 1 and far = 0. The finite far is kept for culling and shadows ([Camera.cpp L184](https://github.com/google/filament/blob/v1.78.0/filament/src/details/Camera.cpp#L184)).
- Depth is `DEPTH32F`, or `DEPTH24` only at feature level 0 ([RendererUtils.cpp L134](https://github.com/google/filament/blob/v1.78.0/filament/src/RendererUtils.cpp#L134)).
- Vulkan, Metal and WebGPU use [0,1] clip space natively. On GL, `glClipControl` is enabled when the extension exists; otherwise the vertex shader remaps z to [−w, w] through `clipControl = (2, −1)` ([OpenGLDriver.cpp L3166](https://github.com/google/filament/blob/v1.78.0/filament/backend/src/opengl/OpenGLDriver.cpp#L3166), [surface_main.vs L261](https://github.com/google/filament/blob/v1.78.0/shaders/src/surface_main.vs#L261)).
- Under Emscripten (WebGL) the extension check is compiled out ([OpenGLContext.cpp L676](https://github.com/google/filament/blob/v1.78.0/filament/backend/src/opengl/OpenGLContext.cpp#L676)), so Filament on the web always takes the remap path. Its own PR says the precision benefit "is mostly lost" there ([#4440](https://github.com/google/filament/pull/4440)).
- `Camera.h` documents the effect for a 32-bit float buffer. With near = 0.001 m, the resolvable step at 1 km is 48.58 m without clip control but 6.1e-5 m with it, and with clip control precision barely depends on near ([Camera.h L104](https://github.com/google/filament/blob/v1.78.0/filament/include/filament/Camera.h#L104)).

**Godot 4: reversed-Z since 4.3, but not where it matters on the web.**

- A depth-correction matrix (flip y, reverse z, remap to [0,1]) is applied only when GPU buffers are filled, so CPU culling keeps a conventional projection ([projection.cpp L787](https://github.com/godotengine/godot/blob/4.7.2-stable/core/math/projection.cpp#L787); PR [#88328](https://github.com/godotengine/godot/pull/88328)).
- The far plane stays finite (defaults near 0.05, far 4000, [camera_3d.h L72](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/3d/camera_3d.h#L72)).
- Forward+ prefers `D32_SFLOAT_S8_UINT`, and Mobile prefers `D24_UNORM_S8_UINT` ([render_scene_buffers_rd.cpp L810](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_rd/storage_rd/render_scene_buffers_rd.cpp#L810)).
- The Compatibility renderer (OpenGL ES 3 and WebGL2, used by web exports) reverses z inside [−1,1] without clip control and uses `GL_DEPTH24_STENCIL8` ([rasterizer_scene_gles3.cpp L1540](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/gles3/rasterizer_scene_gles3.cpp#L1540), [texture_storage.cpp L2637](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/gles3/storage/texture_storage.cpp#L2637)). Maintainers measured "no visible advantage" there (#88328).
- There is no log depth.

**osgEarth: log depth plus a near/far clamp tuned for the globe.**

- `LogarithmicDepthBuffer` has two modes. One writes `gl_FragDepth` (Outerra formula, C = 0.001, far taken from the projection matrix). The other is vertex-only and writes the log value into clip z ([LogDepthBuffer.glsl](https://github.com/gwaldron/osgearth/blob/osgearth-3.8.1/src/osgEarth/LogDepthBuffer.glsl), [LogDepthBuffer.VertOnly.glsl](https://github.com/gwaldron/osgearth/blob/osgearth-3.8.1/src/osgEarth/LogDepthBuffer.VertOnly.glsl)).
- The header names the trade-off. Fragment depth "defeats early-Z testing on the GPU". Vertex-only needs fine tessellation, or large polygons that cross the near plane get clipped ([LogarithmicDepthBuffer L38](https://github.com/gwaldron/osgearth/blob/osgearth-3.8.1/src/osgEarth/LogarithmicDepthBuffer#L38)).
- The examples install the vertex-only mode by default ([ExampleResources.cpp L292](https://github.com/gwaldron/osgearth/blob/osgearth-3.8.1/src/osgEarth/ExampleResources.cpp#L292)).
- `AutoClipPlaneCullCallback` clamps the near and far that OSG computes from bounding volumes. The far plane is clamped to the tangent distance `sqrt(d² − Rpolar²)` ([AutoClipPlaneHandler.cpp L217](https://github.com/gwaldron/osgearth/blob/osgearth-3.8.1/src/osgEarth/AutoClipPlaneHandler.cpp#L217)). That ignores terrain beyond the tangent point, so distant peaks can be clipped. The near/far ratio ramps from 1e-5 to 5e-5 over 0–250 m above terrain, with near ≥ 1 m ([L155](https://github.com/gwaldron/osgearth/blob/osgearth-3.8.1/src/osgEarth/AutoClipPlaneHandler.cpp#L155)).
- Annotations avoid z-fighting with terrain through `DepthOffset`, which pulls vertices toward the eye in view space by a bias that grows with range (defaults 100 m → 10 km bias over 1 km → 10,000 km range; [DepthOffset.glsl](https://github.com/gwaldron/osgearth/blob/osgearth-3.8.1/src/osgEarth/DepthOffset.glsl)).

**iTowns: three.js log depth with fixed planes.**

- `c3DEngine` creates `WebGLRenderer` with `logarithmicDepthBuffer: true` by default ([c3DEngine.js L28](https://github.com/iTowns/itowns/blob/v2.46.0/packages/Main/src/Renderer/c3DEngine.js#L28)).
- `GlobeView` fixes near = max(15 m, 2.352e-6·a) = 15 m and far = 10·a ≈ 63,781 km ([GlobeView.js L94](https://github.com/iTowns/itowns/blob/v2.46.0/packages/Main/src/Core/Prefab/GlobeView.js#L94)). The planes are not fitted, so anything closer than 15 m is clipped.
- Depth picking renders a depth material packed into RGBA and inverts the log formula on the CPU ([c3DEngine.js L230](https://github.com/iTowns/itowns/blob/v2.46.0/packages/Main/src/Renderer/c3DEngine.js#L230)).
- A dynamic near/far was proposed instead of log depth ([#1065](https://github.com/iTowns/itowns/issues/1065)) but was never merged.

**Cost of writing fragment depth.** A shader that writes depth forces the depth test to run after shading. GPUs then lose early-Z and usually hierarchical-Z rejection, and tile-based GPUs bypass hidden-surface removal for those fragments. Under MSAA, one depth value is applied to every covered sample, so edges where surfaces intersect alias. osgEarth's header ([L38](https://github.com/gwaldron/osgearth/blob/osgearth-3.8.1/src/osgEarth/LogarithmicDepthBuffer#L38)), three.js [#17384](https://github.com/mrdoob/three.js/issues/17384), [#22017](https://github.com/mrdoob/three.js/issues/22017) and [#29445](https://github.com/mrdoob/three.js/pull/29445), and Cesium [#4653](https://github.com/CesiumGS/cesium/issues/4653) all report this. Cesium's `discard` outside the frustum range has the same effect. None of the projects publishes measurements of the cost, so it has to be measured (§10).

## 5. Precision measured for this survey

A float32-emulation script written for this survey (it becomes the M2 analytic unit test, §10) emulates shader arithmetic and the storage format. For each distance it searches for the smallest separation whose stored depth still orders correctly. Near is 0.1 m and far is 1e8 m (needed by the finite-far schemes). Each value is the worst case over 12 nearby distances.

| Scheme (storage)                                     | 1 m    | 100 m        | 1 km    | 10 km   | 100 km      | 1,000 km | 10,000 km |
| ---------------------------------------------------- | ------ | ------------ | ------- | ------- | ----------- | -------- | --------- |
| Standard GL [−1,1] (24-bit, WebGL2 canvas)           | 0.9 µm | 8.4 mm       | 0.85 m  | 41 m    | 1.7 km      | 678 km   | fails     |
| Standard [0,1] (float32)                             | 0.6 µm | 5.8 mm       | 0.58 m  | 37 m    | 3.3 km      | 398 km   | fails     |
| Reversed, no clip control (float32)                  | 0.3 µm | 2.8 mm       | 0.28 m  | 29 m    | 1.7 km      | 678 km   | fails     |
| Reversed infinite far, [0,1] (24-bit)                | 0.5 µm | 5.6 mm       | 0.59 m  | 16 m    | 1.7 km      | 118 km   | fails     |
| **Reversed infinite far, [0,1] (float32)**           | 0.1 µm | 10 µm        | 0.11 mm | 0.96 mm | 15 mm       | 94 mm    | 0.5 m     |
| **Fragment-written reversed `near·(1/w)` (float32)** | 0.1 µm | 18 µm        | 0.11 mm | 1.8 mm  | 15 mm       | 94 mm    | 1.5 m     |
| Log, three.js WebGL formula (24-bit)                 | 1.9 µm | 0.12 mm      | 1.1 mm  | 13 mm   | 0.12 m      | 1.3 m    | 12.5 m    |
| Log, three.js WebGPU formula (float32)               | 0.2 µm | 54 µm        | 0.66 mm | 13 mm   | 0.12 m      | 1.2 m    | 13.5 m    |
| Multi-frustum, ratio 1000 (24-bit)                   | 0.8 µm | 7 µm–0.9 mm* | 0.6 mm  | 78 mm   | 7 mm–0.5 m* | 0.7 m    | 99 m      |

\* Depends on where the distance falls inside its frustum.

Findings:

1. **Reversed-Z needs both a [0,1] clip space and float storage.** Then it reaches about 1e-7·d, the precision of the float32 view distance itself, independent of near (near = 1 m gives the same row, as in Filament's table). Without clip control, or with 24-bit storage, it is no better than standard depth, which explains Godot Compatibility, Babylon on WebGL and Filament on the web.
2. **Logarithmic depth is about 10× coarser (about 1.2e-6·d)**, needs a finite far and costs early-Z, but still resolves 13 mm at 10 km.
3. **Writing the reversed value `near·(1/w)` as fragment depth into a float32 attachment recovers reversed-float precision without clip control.** `gl_FragCoord.w` is the perspective-correct 1/w, so no tessellation is needed. It costs early-Z like log depth but is about 10× finer and stores the same value as the clip-control path.
4. For F055 (camera at 1 m, geometry from 0.5 m to the horizon about 3.6 km away, terrain hundreds of kilometers away), standard 24-bit depth fails by meters; reversed float has two orders of magnitude of margin.

## 7. How they test depth

- **CesiumJS:** Jasmine specs render real WebGL frames. `MultifrustumSpec` places billboards at 50 m, 50 km and 50,000 km, checks pixel colors in each frustum, and asserts that log depth reduces three frustums to one ([L360](https://github.com/CesiumGS/cesium/blob/1.146/packages/engine/Specs/Scene/MultifrustumSpec.js#L360)). `SceneSpec` covers the log-depth default override, and `DepthPlaneSpec` covers the depth plane. Model specs note cases "clipped if log depth is disabled". For manual inspection there are `debugShowFrustums` and `debugShowFrustumPlanes`.
- **three.js:** Puppeteer end-to-end screenshot comparison of examples, including the side-by-side `webgl_reversed_depth_buffer` and `webgpu_reversed_depth_buffer` (normal, log, reversed) and both `*_logarithmicdepthbuffer` examples. QUnit covers `Matrix4.makePerspective` and `Frustum`. Most reversed-depth bugs were found by users, not tests.
- **Babylon.js:** Playwright visualization tests against reference images per engine (WebGL2 and WebGPU): "Reverse depth buffer and shadows", "... CSM shadows", and "Reverse depth buffer fix flicker" (WebGPU only). None of the 888 visual tests covers log depth.
- **Filament:** `test/depth_test.cpp` computes, with `nextafter` on float32, the depth step at each distance for each projection convention; this is the source of the `Camera.h` tables. Backend tests compare rendered images (`DepthAndStencilBuffer.png`).
- **Godot:** doctest unit tests check the exact depth-correction matrices ([test_projection.cpp L288](https://github.com/godotengine/godot/blob/4.7.2-stable/tests/core/math/test_projection.cpp#L288)). There is no automated depth-precision rendering test.
- **osgEarth:** no automated rendering tests; manual examples with `--nologdepth` and `--logdepth2` switches.
- **iTowns:** Puppeteer functional tests compare depth-buffer picking with ray-cast range within 2 ‰. The test is currently disabled (`xit`, [misc_clamp_ground.js L54](https://github.com/iTowns/itowns/blob/v2.46.0/test/functional/misc_clamp_ground.js#L54)). Other tests pick from depth in the 2.5D view.

None of them tests temporal z-fighting (pixels alternating across frames). None checks precision analytically against a budget, and none runs a no-clip-control WebGL path in CI. VibeGlobeEngine's tests fill those gaps (§10).

## 10. Chosen approach

[ADR 0005](../adr/0005-depth-strategy.md) decides the following.

**One depth encoding everywhere.** Every path stores depth as `z = near / d` (reversed, infinite far), where d is the distance along the view axis. Depth is 32-bit float, cleared to 0, and tested with `greater-equal` (what three.js maps its default `LessEqualDepth` to under reversed depth).

**Three runtime paths, chosen by capability.**

- **WebGPU:** the [0,1] projection is used natively with a `depth32float` attachment; nothing writes fragment depth.
- **WebGL2 with `EXT_clip_control`:** `clipControlEXT(LOWER_LEFT, ZERO_TO_ONE)` uses the same matrix, and the scene renders into a framebuffer with a `DEPTH_COMPONENT32F` attachment (MSAA renderbuffer of the same format), never the 24-bit canvas.
- **WebGL2 without it:** the same reversed infinite projection is re-expressed for [−1,1] clip space (`z_clip = 2·near − w`), so clipping stays correct. Every scene shader writes `gl_FragDepth = near / viewDepth` (perspective-correct, e.g. `near · gl_FragCoord.w`) into `DEPTH_COMPONENT32F`, with the same compare and clear as the other paths.

**Planes.** The far plane is infinite for depth, and the CPU horizon distance is used only for culling. Near is `min(0.1 m, 0.5 × camera clearance above terrain)`, floored at 1 mm. With reversed float, precision does not depend on near (§5), so per-frame fitting adds nothing but risk. This changes the "Proposed" plan in [architecture](../plan/architecture.md) §4: the fallback becomes fragment-written reversed depth instead of log depth, near/far fitting is replaced by an infinite far and a near tied to camera clearance, and multi-frustum is not planned.

**Layering.** Polygon offset and depth bias are not used. Draped data renders in the terrain pass, as the architecture already decides. Lines and markers that must sit visibly above terrain get a view-space pull toward the eye that grows with distance (osgEarth's idea), the same on every path.

**three.js r186 integration.**

- Create the renderer with `WebGPURenderer({ reversedDepthBuffer: true })` and never `logarithmicDepthBuffer`. After `init()`, read `renderer.reversedDepthBuffer`: false means WebGL2 without clip control, and the engine switches to the fragment-depth path through each material's `depthNode` and `depthFunc` and a clear depth of 0.
- Attach an explicit `DepthTexture` of `FloatType` to every scene target, because r186 defaults to 24-bit.
- The engine writes the projection matrix itself.

**What M2 must measure, and how.**

1. **Analytic unit test.** Emulate each path's float32 arithmetic with `Math.fround`. Assert monotonic ordering and a resolvable step ≤ 3e-7·d over [near, 4e7 m] for the clip-control paths and ≤ 5e-7·d for the fragment path.
2. **Scenario `?scenario=depth-range` (F055).** The camera is 1 m above ground looking at the horizon. Quad pairs 1, 2 and 5 cm apart stand at 0.5 m to 10 km, scaled to stay visible, plus a draped line and a marker. Record 120 static frames and 120 frames with sub-pixel jitter, and check order colors and frame differencing for oscillating pixels (`quality.md`). Run on WebGPU, on forced WebGL2 with clip control, on forced WebGL2 with an engine switch that ignores clip control (in Chrome), and in Firefox.
3. **Depth readback.** Reconstruct positions from read-back depth against the analytic surface within 1e-6·d on every path.
4. **Performance.** Use timestamp queries (WebGPU `timestamp-query`, `EXT_disjoint_timer_query_webgl2`) in a tilted, high-overdraw terrain view at 1080p on the reference desktop and tablet. Compare the fragment-depth path with the clip-control path on the same device. If the fragment path costs more than 1.25× GPU time, record it in the ADR and evaluate a two-frustum split for that path only.

## 11. Open questions

- When Firefox ships `EXT_clip_control` (it has an implementation that depends on driver capability), the fragment path shrinks to old browsers. Re-check the share each release.
- If a WebGPU shader ever needs to write depth (ray-cast atmosphere or ellipsoid impostors), check whether the WGSL `fragment_depth` extension (conservative `frag_depth`) is available, so early-Z can be kept.
- Stencil: if a later milestone needs stencil in the main pass, `depth32float-stencil8` is optional in WebGPU. Measure its availability on reference devices before designing with stencil, and never fall back to `depth24plus-stencil8`.
- Depth consumers in later milestones (fog, atmosphere, labels occluded by terrain, post effects) must use the shared `near / z` reconstruction. In r186, stock three.js post-processing nodes treated depth ≥ 1 as background, so SSAO darkened and denoising blurred the background with reversed depth. [#34792](https://github.com/mrdoob/three.js/pull/34792) fixes this for r187; check each node before use.
- Upgrading to three.js r187 (float default depth, MSAA blit fix) is a pinned-version decision for the renderer ADR.
